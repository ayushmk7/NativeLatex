# Landing: Virgule candidate rename plan

Status: planning only · 2026-11-18 · written against `main` at `840319f` (this worktree's branch lags it). Virgule is a candidate name, not an approved rebrand. Nothing here has been changed, published or deployed.

## Name gate (blocks every public step)

An iPhone/iPad news app is already called Virgule (App Store ID 1245101112), and a preliminary search found a Canadian VIRGULE trademark listing that mentions software. Neither has been assessed; this plan does not claim the name is clear or that the listing applies. **Public-rename hold:** no landing commit that shows Virgule reaches `main` until the coordinator records a completed name review. The hold matters because `.github/workflows/pages.yml` deploys on every push to `main` that touches `landing/**`, so merging is publishing.

## Smallest complete change set (once the name is approved)

1. **Copy.** Replace the visible name in the roughly 10 `index.html` strings. Keep the copy accurate: the app opens and edits LaTeX, Markdown, plain text and other supported text files. The current meta description says "writing LaTeX and Markdown"; widen it to "LaTeX, Markdown and other text files" so it doesn't suggest only one or two formats, and keep "native Mac app".
2. **Icon.** Take the regenerated `landing/icon.svg` from Art's `gen.py` output (label and mark). Landing does not edit it by hand.
3. **Media.** Take re-captured footage and stills from Brag if the app's in-frame name changes. Keep the **existing file paths** (`media/libreweave-*`) through the transition because the README and any outside embeds link to them by URL. Renaming the files is a separate, later step, done only once the old host redirects media (see 5).
4. **Theme key.** Leave `libreweave-theme` as it is. A new origin starts with empty storage anyway, and visitors never see the key. Rename it only if the coordinator wants no old strings left in the source.
5. **Hostname.** Candidate: `virgule.ayushmadhav.com` (to be decided). GitHub Pages allows one custom domain per repository, so the old host needs its own redirect. Two options:
   - **A. Vercel 301 (recommended if the owner accepts Vercel Hobby's non-commercial terms).** Repoint the old record from `ayushmk7.github.io` to a Vercel project containing only `vercel.json` with `{"redirects":[{"source":"/(.*)","destination":"https://<new-host>/$1","permanent":true}]}`. This gives a real 301 for every path, MP4 and GIF included, and the DNS is already in Vercel.
   - **B. GitHub-only.** Create a second public repo whose Pages custom domain is the old host. It serves an `index.html` and `404.html` that redirect to the same path on the new host (`<meta http-equiv="refresh">` plus `location.replace` and `rel=canonical`), and keeps **copies** of the `media/` files at their old paths, because an HTML redirect cannot serve an `.mp4` or `.gif`. The old DNS record stays as it is (it already points at `ayushmk7.github.io`). There is no true 301, so search engines consolidate more slowly.
6. **SEO.** Add one `<link rel="canonical" href="https://<new-host>/">` so the old and new hosts consolidate. Open Graph/Twitter tags and a social image are a **new feature** that the rename doesn't require; add them only if the coordinator asks, with the image from Art.
7. **Inbound links.** Update `README.md` lines 15–16 to the new host in the same merge that switches the domain (Brag owns README; Landing flags it). Update the host in the five docs listed above.
8. **Workflow.** `pages.yml` itself needs no change. Leave the repo name and GitHub links alone unless Backend or the coordinator renames the repo; GitHub redirects old repo URLs after a rename anyway.

## Sequencing and dependencies

1. Name review approved → coordinator lifts the hold. (Blocks everything below.)
2. Art delivers the icon; Brag delivers media if the footage changes. (Landing copy can be prepared in parallel.)
3. Add the new DNS record: `<new-host>` CNAME → `ayushmk7.github.io` in Vercel DNS. Wait for it to resolve.
4. Prepare the old-host redirect (option A project, or the option B repo), deployed but **not yet** on the old hostname.
5. One merge to `main`: copy, icon, canonical, README links, docs. Then switch the Pages custom domain to `<new-host>` in the same window. Wait for the certificate, then enforce HTTPS.
6. Immediately attach the old hostname to the redirect (A: repoint the old DNS record to Vercel; B: set the old host as the second repo's Pages domain). Between steps 5 and 6 the old host returns GitHub 404s, so keep that gap to minutes.
7. Optional, later: rename media files, keeping the old paths redirected.

Dependencies: Art (icon), Brag (media, README), Backend (any repo rename), coordinator (name, hostname, redirect option).

## Reversible internal prototype path

Do all prototype work on the `landing` branch only, and never merge it to `main` while the hold is in place. Preview locally with `python3 -m http.server 4173 --directory landing`. Do not use a Vercel preview, a second Pages site, or a public preview URL, since each of those publishes the name. Reverting means deleting the branch commits, and nothing public changes.

## Fallback if Virgule is rejected

Nothing public will have changed: the live site stays LibreWeave at `libreweave.ayushmadhav.com`. Drop the prototype commits. The same change set and sequence apply to whichever name is chosen next, with only the strings, hostname and Art/Brag assets swapped in.

## Validation that would prove completion

- `curl -sI https://<new-host>/` returns 200 from GitHub with a valid certificate, and `gh api repos/ayushmk7/NativeLatex/pages` shows the new `cname` with `https_enforced: true`.
- `https://<old-host>/`, `/media/libreweave-demo.mp4` and `/media/libreweave-demo-preview.gif` reach the same path on the new host (A: `curl -sI` shows 301 with the right `Location`; B: HTML redirect for pages and HTTP 200 for the media copies).
- `https://ayushmk7.github.io/NativeLatex/` redirects to the new host.
- `grep -ri libreweave landing/` matches only the intentionally kept media paths and the theme key. The rendered page text, title, meta description, `aria-label`s and icon label show only the new name.
- Repeat the existing headless Chrome checks from `landing-plan.md` at 1440×900 and 390×844 in both appearances: theme follows the system and persists, BB-8 works by keyboard, no overflow, video autoplays muted and loops, no console errors or failed requests, `#2563EB` is the only blue, no download call to action.
- README MP4 links and the host link return 200 or the 301 chain to 200.

## Migration and rollback risks

- **Gap 404s.** The old host serves nothing between the Pages domain switch and the redirect attachment. Mitigation: prepare the redirect first and do steps 5 and 6 together.
- **Media embeds.** Any HTML-only redirect breaks direct `.mp4`/`.gif` URLs. Mitigation: a true 301 (A) or media copies (B).
- **Certificate delay.** Pages may take minutes to hours to issue the new certificate, and HTTPS can't be enforced until it does. Mitigation: add the DNS record early (step 3).
- **Cached DNS.** As noted in `deployment-plan.md`, cached records can briefly reach Vercel's wildcard.
- **Rollback.** Set the Pages custom domain back to `libreweave.ayushmadhav.com`, repoint the old DNS record to `ayushmk7.github.io`, and revert the merge commit (push to `main` redeploys). Keep the old host's redirect in place for at least the life of any shared links; never let the old hostname lapse or be reused.
- **Name exposure.** Adding the new DNS record publishes the hostname in DNS before launch. Mitigation: do step 3 only after the name is approved.
