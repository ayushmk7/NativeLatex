## Decision before implementation

`Virgule` has an existing [iPhone/iPad news app](https://apps.apple.com/ro/app/virgule/id1245101112). A [preliminary Canadian trademark listing](https://www.trademarkelite.com/canada/trademark/trademark-detail/918493/VIRGULE) also mentions software; its scope and status have not been assessed for this product. Treat the name and slash mark as **uncleared candidates**. Review LibreWeave in the same pass: it is the current public name, but has not received the proposed review either. Keep the public app, icon, landing page, GitHub repository, and download unchanged until the review records a go/no-go decision. An internal prototype may live on a private branch without entering an installed or public build.

**Recommended identity choice:** keep the current bundle ID `app.libreweave.LibreWeave` through a visible rebrand. macOS uses it for preferences, recent documents, window state, and default file handlers. Change the product and display name, icon, README, media, and site; the target, scheme, Swift module, and internal ID can keep their current names because users do not see them. Changing `PRODUCT_NAME` also requires updating the hard-coded test host in the same edit. If a literal internal rename is required, make one move to a permanent name-neutral ID **before** the first public Developer ID release, migrate the appearance and build-owner token from LibreWeave then LibreLeaf **in the same commit as the ID change**, and accept that Open Recent and Finder default choices will need resetting. The hidden `.libreleaf-build`, `.libreleaf-owner`, and `LibreLeaf.log` names must stay: they protect ownership of existing TeX output.

The adversarial review found that this Mac's old LibreLeaf build-owner token differs from its current LibreWeave token. The earlier migration landed after the ID change, so some older build folders are already orphaned, though none were deleted. A new ID must not repeat that sequence. A rename should reuse a folder owned by the **current** token and must never delete or take over an unowned folder.

## Order of work after the name decision

1. **Private design check.** Art explores at least two genuinely new slash-mark treatments on an isolated branch. Compare them against the existing Virgule app icon and at 16, 32, 256 and 512 px in light, dark, clear and tinted appearances. Use `#2563EB` as the only brand blue, with no inner tile or page frame. Test the clear-light mark in the live Dock over light and grey wallpapers and the tinted mark at 16 px; static renders alone do not prove legibility. Use an isolated test session so the owner's desktop is not changed. The proposed white Mono layer is a hypothesis, not a passed contrast result. Use live text in the landing header unless a proposed outlined font has a confirmed suitable licence. The BB-8 control and app layout remain consistent with the current design.
2. **Freeze identity and migration.** Decide whether to retain the current bundle ID (recommended) together with the first signing plan. Make a backup of the installed app before an eventual replacement. Keep the document-type declarations and handler ranks unchanged. If the ID changes, land the migration chain atomically with that change; never build or test an intermediate ID without it. Test both the LibreWeave → new-domain migration and the earlier LibreLeaf fallback before installing the candidate app.
3. **Rename the visible Mac build.** Update `PRODUCT_NAME`, `CFBundleDisplayName`, executable/test host and visible strings together. Keep the target/scheme and Swift module unless there is a concrete need to change them; this avoids breaking generated scheme commands and `@testable import` callers. Update the Design demo and Integrations copy that users see. Keep brand-bearing legacy IDs where migration and existing files depend on them. Do not add a cross-package naming layer solely for a one-time replacement.
4. **Replace art and inspect the app.** Promote the chosen Icon Composer layers, flat marks and favicon from the prototype. Build the universal app and inspect the actual compiled icon in all macOS styles. Confirm the menu, Dock, Finder Open With, Settings and VoiceOver say the new name and the editor still opens LaTeX, Markdown and plain text.
5. **Rebuild public media.** The current demo hook/outro and GIF contain LibreWeave. Brag re-renders both dark and light cuts from the existing offscreen footage if their visible UI remains valid; otherwise it re-captures without stealing the owner's screen. Refresh README copy, screenshots, alt text, links and video together. Keep the existing `landing/media/libreweave-*` paths through the cutover so old direct media links continue to work; their file names are not user-visible branding. Decide whether the unmerged light-cut commit `e16830c` is included before this step.
6. **Cut over the site.** After the name review passes, prepare the new hostname and a real HTTPS redirect for `libreweave.ayushmadhav.com`, including old `/media/*` URLs. Then update the GitHub Pages custom domain, landing copy, favicon, canonical URL and README links in one release window. A DNS CNAME alone cannot redirect an old URL. If the old host instead stays on a separate static site, it must continue serving direct media files at their old paths. The BB-8 theme choice resets on a new hostname because browser storage is tied to the site origin. Do not claim a public Mac download until a Developer ID archive is signed, notarized, stapled, downloaded and tested.
7. **Review and release.** The adversarial workspace checks the combined diff and the evidence below. Only then replace the local installed app or publish the site/repo rename. Keep the old app and site recoverable until the new paths and associations work.

## Completion evidence

- `git grep` finds no old name in user-visible app strings, landing copy, README text or accessibility labels; screenshots and video frames get a separate visual audit. Intentional legacy identifiers are listed and left intact, including `libreweave-theme`, Markdown style keys, and `.libreleaf-*` build output names.
- Full Xcode app tests and all three local Swift package suites pass. A Release archive has the expected product name, bundle ID, UTIs, both architectures, icon stacks and code-signing entitlements.
- An upgrade check on this Mac preserves the BB-8 appearance choice and reuses an existing `.libreleaf-build` output folder owned by the current token. Older folders with a different token remain untouched. Opening `.tex`, `.md` and `.txt` from Finder and Open With works; the owner's existing default choices remain if the bundle ID stays stable. A clean-Mac check covers TeX present and absent states. Inspect the registered app path because stale copies in Trash, `dist/` and temporary build directories can confuse LaunchServices even with a stable ID.
- The built icon is visually inspected at small sizes in default/light, dark, clear and tinted styles; the mark is new, legible, and has no box inside the icon body.
- Both landing appearances pass the current 1440 px and 390 px checks. The demo autoplays muted and loops, all media and GitHub links resolve, the new site has valid HTTPS, and the old host redirects both pages and direct media requests.
- A public app, when available, passes `codesign --verify --deep --strict`, Gatekeeper assessment and `stapler validate` after a real download. The current ad-hoc build does not satisfy this gate.

## Rollback and open decisions

Keep the old installed app as a dated backup outside Applications and retain the current branch/tag so the weave art and old site can be restored. Never edit source documents or delete TeX output during a rename. If the name review rejects Virgule, discard the prototype and keep LibreWeave live; another name can reuse this plan after the brand-specific art and URLs are swapped.

Before implementation, settle: (1) name and mark review for both Virgule and LibreWeave, (2) bundle ID continuity versus a one-time neutral ID, (3) the final slash icon treatment, (4) whether to rename the GitHub repository after the app and site are ready, and (5) the service that will keep old-host pages and media reachable. Keep the existing media file paths unless a separate redirect plan proves new paths safe. No other product features are needed to complete the rebrand.
